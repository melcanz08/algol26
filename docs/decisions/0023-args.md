# ADR 0023: `args()` — command-line arguments

Status: Accepted

## Context

ALGOL26 has no way to read the process's command-line
arguments. `main` takes no parameters; there is no `argv`
builtin.

## Decision

Add a builtin:

    args() -> List<String>

Returns the arguments passed to the process, excluding the
program name. Returns an empty list if no arguments were given.

### Interpreter

`Interpreter::with_args` stores a `Vec<String>`; `args()`
returns it as `RuntimeValue::List`. `Interpreter::new` seeds
the list from `std::env::args().skip(1)`. Tests inject a known
list via `with_args` without a subprocess.

### LLVM and WASM refusal

Neither backend exposes C `argc`/`argv` to the language's
`main`. Both refuse programs that call `args()` via the
capability check (`Feature::CommandLineArgs`). A follow-up ADR
may add an LLVM implementation by capturing `argc`/`argv` in
an LLVM `main` shim.

### Why a builtin, not `main(args: List<String>)`

Changing `main`'s signature touches entry-point lookup in the
interpreter and both backends' `main` registration. The
builtin form reuses the existing call path: `FunctionCall` ->
`Instruction::Call` -> backend dispatch.

## Backends

| Backend | Support |
|---|---|
| Interpreter | Yes — reads `std::env::args().skip(1)` |
| LLVM | Refused — capability check |
| WASM | Refused — capability check |

## Consequences

**Positive.** Programs can read their arguments on the
interpreter, unblocking CLI-shaped applications.

**Negative.** The CLI (`algol26 run foo.gol -- arg1 arg2`)
does not yet pass user arguments through to the program; the
interpreter's `args()` returns the compiler's own arguments in
that case. A follow-up will either introduce a `--` separator
or extend `run_interpreter` to accept a program-args vector.
