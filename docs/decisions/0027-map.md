# ADR 0027: `Map<K, V>` — key-value container

Status: Accepted (design); implementation pending

## Context

ALGOL26 has four container types — `List<T>`, `Array<T, N>`,
`Option<T>`, `Result<T, E>` — and one channel type. None of them
is keyed. Programs that need to look up a value by a key
(currently: config parsing, grouping rows by a column, storing CLI
flags) fall back to parallel `List<K>` / `List<V>` pairs with a
linear scan on every lookup, which is O(n²) and three times the
code.

Three modules in the outsider's proposal are blocked by this:

- `config.gol` — a config file is definitionally key-value.
- `analysis/aggregate.gol` — grouping rows by a column requires a
  bucket per key.
- `cli.gol` — flag storage is key-value.

Two more would become natural:

- `output/json.gol` — flat JSON objects are key-value (recursive
  objects additionally need sum types, see ADR 0028 if it exists).
- `data/model.gol` — records get stored in indexed tables.

Map is the single highest-leverage feature on the remaining-work
list. It unblocks more modules per unit of implementation than
anything else.

## Decision

Add a builtin generic container type `Map<K, V>`.

Map is a builtin, not a user-definable type. ALGOL26 cannot
express hash functions, hash tables, or equality dispatch in the
language itself, so a user-definable Map would be a library
written in a language that cannot host it. Same reasoning as
`List`, `Option`, `Result`, and `Channel`.

### Key types

Keys are restricted to `Int`, `String`, and `Bool`.

Records, lists, and other maps are not hashable without a
user-provided hash function and equality predicate. Floats are not
hashable because `NaN != NaN` and the hashing contract breaks.
`Ptr` is not hashable because two equal pointers do not
necessarily represent the same value.

The analyzer rejects any `Map<K, V>` where `K` is not one of the
three permitted types. The diagnostic is `E0002: Map keys must
be Int, String, or Bool, found {type}`.

`Type::Unknown` keys are accepted at analysis time only when the
type cannot yet be resolved (e.g. inside a generic function body
before substitution). The IR verifier rejects `Unknown` keys at
the point of use.

Value types are unrestricted.

### Syntax

**Construction with entries:**

    val counts := Map { "a": 1, "b": 2, "c": 3 }

Key and value types are inferred from the entries. If all keys are
`String` and all values are `Int`, the result is
`Map<String, Int>`.

Mixed key or value types follow the same rule as list literals:

    val mixed := Map { "a": 1, "b": 2.5 }
    // Map<String, Float>, with an implicit Int→Float coercion
    // on the "a" entry.

    val bad := Map { "a": 1, 2: 3 }
    // Error: key types String and Int have no common supertype.

**Empty construction:**

    val empty := Map<String, Int> {}

The empty literal requires explicit type arguments. There are no
entries to infer from, so the analyzer has nothing to work with
unless the expected type provides it:

    var config: Map<String, String> := Map {}
    // Type inferred from the annotation; `Map<String, String> {}`
    // is not required.

Both forms parse. The parser sees `Map`, optionally parses
`<` Type `,` Type `>` (expression-level type arguments, see
"Parser notes" below), then expects `{`. The braces may be empty.

**Operations, method-form:**

    m.insert(k, v)          // mutating; requires `var m`
    m.get(k)                // -> Option<V>
    m.contains(k)           // -> Bool
    m.keys()                // -> List<K>
    m.values()              // -> List<V>
    m.length()              // -> Int

`insert` overwrites an existing key silently. To insert
conditionally, use `if not m.contains(k) then m.insert(k, v)`.

`get` returns `Option<V>`. `None` means "key not present." A
value that is itself an `Option` produces a nested `Option`, which
is unambiguous: `Some(None)` means "key present, value is None";
`None` means "key absent."

**Iteration:**

    for k in m.keys()
        print(k)
        print(m.get(k))

Iteration is over the key list, which is a snapshot taken at the
time `.keys()` is called. Mutation during iteration affects the
map, not the snapshot. This is the same behavior `List` iteration
has today.

Iteration order is unspecified. Implementations may return keys
in hash order, insertion order, or any other order; programs that
depend on a specific order should sort the key list first.

### Type system representation

    Type::Map(Box<Type>, Box<Type>)

`Map<String, Int>` is `Type::Map(Box::new(Type::String), Box::new(Type::Int))`.

**Mangling** (for generic instantiation): `Map_<key>_<value>`, using
`mangled_type_name` on each component. Same shape as `List_<inner>`
and `Pair_<name>_<arity>_<args>`.

**Coercion:** `Map<K1, V1>` coerces to `Map<K2, V2>` when
`K1.can_coerce_to(K2)` and `V1.can_coerce_to(V2)`. This matches the
existing covariance rule for `List<T>`, and carries the same
soundness caveat: if a `Map<String, Any>` were aliased as a
`Map<String, Int>`, an insert through the alias could produce a
runtime type mismatch. In practice the language has no `Any` type
and no record subtyping, so the caveat is theoretical. Noted here
so a future author who adds subtyping sees the interaction.

**Display:** `Map<K, V>`.

**`from_str`:** parse `map<K, V>` case-insensitively, both `<` and
`[` bracket forms, matching the existing `List<T>` / `List[T]`
handling.

**Copy semantics:** `Map<K, V>` is never `Copy`. Maps own
heap-allocated storage. `is_copy` returns `false` unconditionally,
matching `List<T>`.

### AST representation

New expression form:

    ExprKind::MapLiteral {
        key_type: Option<TypeSyntax>,
        value_type: Option<TypeSyntax>,
        entries: Vec<(Expr, Expr)>,
        span: Span,
    }

`key_type` and `value_type` are `Some` only for the explicit form
`Map<K, V> { ... }`. For the inferred form `Map { ... }`, both are
`None`.

No new statement form. `m.insert(...)` and `m.get(...)` are
existing `ExprKind::FunctionCall` with a dotted name, dispatched
through the builtin method registry.

No new pattern form. Maps are not destructurable in `match`. The
iteration pattern (`.keys()` + `.get()`) covers the use cases.

### Parser notes

Map literals introduce **expression-level type arguments** — the
first occurrence of this in the language. The syntax `Map<K, V> {}`
requires the parser to disambiguate `<` after an identifier in
expression position.

The disambiguation rule: after an identifier, if the next token is
`<` and the tokens that follow match `<` Type (`,` Type)* `>` `{`,
the `<...>` is a type argument list. Otherwise `<` is a comparison
operator.

Lookahead depth: unbounded in principle, but bounded in practice
by the nesting depth of type arguments. A simple scanner over the
token stream — advance until the matching `>`, checking that every
token in between is a valid type-syntax token — decides in linear
time.

This is the same disambiguation that records deferred for
`Pair<Int> { first: 1 }`. Records deferred it because no record
construct needed it. Maps do: the empty literal `Map<String, Int> {}`
cannot be written any other way. So the parser change lands with
Map, and records can later opt into `Pair<Int> { ... }` for free.

### IR representation

New value variant:

    TypedIRValue::Map {
        key_type: Type,
        value_type: Type,
        entries: Vec<(TypedIRValue, TypedIRValue)>,
    }

Entries are a `Vec`, not a `HashMap`. The IR is a compile-time
snapshot; the runtime decides how to store it.

New instructions: none. `m.insert(...)` lowers to a `Call` to
`Map.insert`, dispatched through the existing builtin path. The
analyzer registers the following builtin signatures:

    Map.insert   : (Map<K, V>, K, V) -> Void       — mutating
    Map.get      : (Map<K, V>, K) -> Option<V>
    Map.contains : (Map<K, V>, K) -> Bool
    Map.keys     : (Map<K, V>) -> List<K>
    Map.values   : (Map<K, V>) -> List<V>
    Map.length   : (Map<K, V>) -> Int

The receiver is passed as the first argument, matching how
`List.length` and `String.concat` already work.

`Map.insert` requires its receiver to be a mutable binding. The
analyzer enforces this the same way it enforces `p.x := 5` on a
record: by checking the receiver variable's `mutable` flag and
rejecting with the existing immutability diagnostic.

### Interpreter representation

New runtime variant:

    RuntimeValue::Map {
        key_type: Type,
        value_type: Type,
        entries: HashMap<MapKey, RuntimeValue>,
    }

where:

    pub(super) enum MapKey {
        Int(i64),
        String(String),
        Bool(bool),
    }

with `#[derive(Hash, Eq, PartialEq, Clone, Debug)]`.

`MapKey` is a new type rather than reusing `RuntimeValue` directly
because `RuntimeValue` contains `Float`, which does not implement
`Hash` (NaN breaks the contract). Restricting the runtime key
enum to the three hashable types mirrors the analyzer's key
restriction exactly, so no runtime check is needed — the key
type is already validated at compile time.

`RuntimeValue::Map` participates in `display`, `runtime_eq`, and
`runtime_kind`:

- `display`: `{"a": 1, "b": 2}` — JSON-ish, deterministic only if
  the map is sorted first (the interpreter does not sort; the
  output order is whatever `HashMap` iteration produces).
- `runtime_eq`: two maps are equal iff same key set and equal
  values for each key. Order-independent.
- `runtime_kind`: `"Map"`.

### Backends

| Backend     | Support                                                        |
|-------------|----------------------------------------------------------------|
| Interpreter | Yes — `RuntimeValue::Map { .. }` with `HashMap<MapKey, RuntimeValue>` |
| LLVM        | Refused — capability check (`Feature::Map`)                    |
| WASM        | Refused — capability check (`Feature::Map`)                    |

The LLVM refusal follows the same reasoning as `Feature::Records`:
lowering a hash map requires a runtime, and ALGOL26 does not have
one. The follow-up LLVM ADR for records can be extended to cover
maps in the same session, or Map can get its own LLVM lowering ADR.
Either way, deferred.

### Capability

New `Feature::Map`. Interpreter claims it; LLVM and WASM do not.

The scanner fires on any `TypedIRValue::Map` or on any `Call` whose
callee name is in `{ Map.insert, Map.get, Map.contains, Map.keys,
Map.values, Map.length }`. The call-name check covers the case
where the map value itself is not visible in the IR — for example,
`m.length()` on a map that came in as a function parameter lowers
to `Call { func: "Map.length", args: [Variable("m"), ...] }`, and
the value scan alone would miss it.

## What is deliberately not in v1

- **`Map.remove(k)`.** Deletion has a return-value design question
  (`Bool` for "was present" vs. `Option<V>` for the removed value)
  and a rehash question (tombstones vs. compaction). Both are
  solvable, neither is needed by the three blocked modules. Add
  when a concrete use case demands it.
- **`Map.is_empty()`.** `m.length() == 0` covers it. Trivial to
  add later if it turns out to be the common idiom.
- **`Map.entries()`.** Returning `List<(K, V)>` would need tuples,
  which ALGOL26 does not have. Deferred with tuples.
- **Iteration in a `for` loop directly over the map.** Requires
  either destructuring in `for` (`for (k, v) in m`) or a
  key-only convention (`for k in m`). Both are language extensions;
  the `.keys()` workaround is explicit and obvious.
- **Ordered maps.** No `Map.ordered` or insertion-order guarantee.
  Hash order is unspecified. Programs that need order sort the
  keys.
- **Custom hash or equality.** No `impl Hash for MyType`. Keys
  are limited to the three builtin hashable types.
- **Nested generic maps in the literal syntax with inferred types.**
  `Map { "a": Map { "b": 1 } }` works because the inner literal's
  types infer from its own entries. `Map { "a": Map {} }` does not
  — the inner `Map {}` has no entries and no expected type at the
  point the analyzer reaches it. The workaround is explicit:
  `Map { "a": Map<String, Int> {} }`. Noted as a known
  limitation, not a design question to resolve now.
- **`Drop` for maps.** Same as records — the language has no
  `Drop`, and maps do not introduce one.

## Consequences

**Positive.**

- Config parsing, aggregation, and CLI flag storage become
  straightforward. Three of the eight flagged modules unblock.
- `Map` is the last big container primitive the language was
  missing. After it, the standard container set (`List`, `Array`,
  `Map`, `Option`, `Result`, `Channel`) is complete.
- The parser change — expression-level type arguments — lands
  once and unblocks generic record literals (`Pair<Int> { ... }`)
  as a follow-up.
- The capability-matrix pattern from ADR 0024 extends naturally.
  No new design work for the LLVM/WASM refusal.

**Negative.**

- Map is the largest single feature on the remaining-work list.
  Realistically 1500+ lines across 15+ files including the
  exhaustiveness cascade.
- The hash-iteration-order nondeterminism is a footgun. Programs
  that print a map or iterate over keys get different output on
  different runs. The `.keys()` + sort workaround is not obvious
  to a new user. Documented in the feature doc; mitigated by
  keeping the surface small.
- The covariance rule for `Map<K, V>` has a theoretical soundness
  hole if the language ever grows subtyping. Noted in the ADR so
  a future author sees it.

**Neutral.**

- `Type::Map` joins `Type::Generic` and `Type::Record` as the
  third parameterized type variant. The pattern is established.
- `RuntimeValue::Map` joins `RuntimeValue::Record` as the second
  builtin-with-a-name runtime variant. No new mechanism.

## Implementation order

1. **Type plumbing** — `Type::Map`, mangling, coercion, Display,
   `from_str`, `substitute`, `contains_type_var`, `contains_unknown`,
   `is_copy`. ~150 lines. Compiles in isolation.
2. **Capability** — `Feature::Map`, scanner rules. ~30 lines.
   Compiles in isolation.
3. **AST + parser** — `ExprKind::MapLiteral`, expression-level
   type arguments, literal parsing. ~250 lines. The type-argument
   parser is the fiddly part.
4. **Analyzer** — Map registration as a builtin container, key
   type validation, `Map.insert` mutation check, entry type
   inference, coercion rules. ~200 lines.
5. **IR** — `TypedIRValue::Map`, builtin signatures for the six
   operations, verifier arms. ~200 lines.
6. **Interpreter** — `RuntimeValue::Map`, `MapKey`,
   `HashMap`-backed operations, `display` / `runtime_eq` /
   `runtime_kind` extensions. ~300 lines.
7. **Tests, feature doc, status row, coverage matrix.** ~400 lines.

Steps 1, 2, and 7 are straightforward. Steps 3–6 are the real
work. Estimated two to three sessions at the pace of the records
implementation.
